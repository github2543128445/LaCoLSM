TimberSaw日志格式
==================
日志文件内容是一系列32KB的数据块。唯一的例外是文件末尾可能包含一个不完整的数据块。

每个数据块由一系列记录组成：

    block := record* trailer?
    record :=
      checksum: uint32     // type和data[]的crc32c校验和；小端序
      length: uint16       // 小端序
      type: uint8         // FULL、FIRST、MIDDLE、LAST之一
      data: uint8[length]

记录永远不会在数据块的最后六个字节内开始（因为放不下）。这里的任何剩余字节构成尾部，
必须完全由零字节组成，读取器必须跳过这些字节。

注意：如果当前数据块正好剩下七个字节，并且要添加一个非零长度的记录，写入器必须发出一个FIRST记录
（其中包含零个字节的用户数据）来填充数据块的最后七个字节，然后在后续数据块中发出所有用户数据。

将来可能会添加更多类型。一些读取器可能会跳过它们不理解的记录类型，其他读取器可能会报告跳过了一些数据。

    FULL == 1
    FIRST == 2
    MIDDLE == 3
    LAST == 4

FULL记录包含完整的用户记录内容。

FIRST、MIDDLE、LAST是用于已被分割成多个片段的用户记录的类型（通常是因为数据块边界）。
FIRST是用户记录第一个片段的类型，LAST是用户记录最后一个片段的类型，
MIDDLE是用户记录所有内部片段的类型。

示例：考虑一系列用户记录：

    A: 长度1000
    B: 长度97270
    C: 长度8000

**A**将作为FULL记录存储在第一个数据块中。

**B**将被分成三个片段：第一个片段占用第一个数据块的剩余部分，第二个片段占用整个第二个数据块，
第三个片段占用第三个数据块的前缀部分。这将在第三个数据块中留下六个空闲字节，这些字节将作为尾部保持为空。

**C**将作为FULL记录存储在第四个数据块中。

----

## 相比recordio格式的一些优势：

1. 我们不需要任何重新同步的启发式方法 - 只需转到下一个数据块边界并扫描。如果有损坏，
跳到下一个数据块。作为附带好处，当一个日志文件的部分内容作为记录嵌入到另一个日志文件中时，
我们不会混淆。

2. 在近似边界处分割（例如，用于mapreduce）很简单：找到下一个数据块边界并跳过记录，
直到遇到FULL或FIRST记录。

3. 我们不需要为大记录额外缓冲。

## 相比recordio格式的一些缺点：

1. 不打包微小记录。这可以通过添加新的记录类型来解决，所以这是当前实现的缺点，
不一定是格式的缺点。

2. 没有压缩。同样，这也可以通过添加新的记录类型来解决。
